# Надёжность

Iceberg проектировался для решения проблем корректности, которые возникают у Hive-таблиц, работающих поверх S3.

Hive отслеживает data files одновременно через централизованный metastore для партиций и файловую систему для отдельных файлов. Такая архитектура делает невозможным атомарное изменение содержимого таблицы, а eventual-consistent хранилища вроде S3 могут возвращать неверные результаты, если состояние таблицы восстанавливается с помощью listing файлов. Кроме того, планирование job требует большого числа медленных listing-вызовов: O(n) от количества партиций.

Iceberg хранит полный список data files для каждого snapshot с помощью персистентной древовидной структуры. Каждая запись или удаление создаёт новый snapshot, который максимально переиспользует metadata tree предыдущего snapshot, чтобы не генерировать избыточный объём записи метаданных.

Допустимые snapshots Iceberg-таблицы хранятся в table metadata file вместе со ссылкой на текущий snapshot. Commit атомарно заменяет путь к текущему table metadata file. Это гарантирует атомарность всех обновлений данных и метаданных и является основой **serializable isolation**.

Отсюда следуют улучшенные гарантии надёжности:

- **Serializable isolation** — все изменения таблицы образуют линейную историю атомарных обновлений;
- **Надёжное чтение** — reader всегда использует согласованный snapshot таблицы без удержания lock;
- **История версий и rollback** — snapshots сохраняются как история, и таблицу можно откатить, если job записал некорректные данные;
- **Безопасные файловые операции** — благодаря атомарным изменениям можно безопасно compact небольшие файлы и добавлять поздно прибывшие данные.

Архитектура также даёт преимущества производительности:

- **O(1) RPC для планирования** — вместо listing O(n) директорий чтение snapshot требует O(1) RPC;
- **Распределённое планирование** — pruning файлов и predicate push-down распределяются по jobs, что убирает metastore как bottleneck;
- **Более мелкая гранулярность партиционирования** — распределённое планирование и O(1) RPC снимают ограничения на fine-grained partitioning.

## Конкурентные операции записи

Iceberg поддерживает несколько конкурентных writers с использованием **optimistic concurrency control**.

Каждый writer предполагает, что других writers нет, и формирует новые table metadata для своей операции. Затем он пытается commit изменение, атомарно заменив текущий table metadata file новым.

Если атомарная замена не удалась, потому что другой writer уже успел выполнить commit, writer повторяет операцию: строит новое metadata tree уже на основе нового текущего состояния таблицы.

### Стоимость повторных попыток

Writers избегают дорогого повторного выполнения работы за счёт того, что изменения структурированы для переиспользования между retries.

Например, append обычно создаёт новый manifest file для добавляемых data files. Этот manifest можно добавить в таблицу при повторной попытке без его полной перезаписи на каждом retry.

### Валидация при retry

Commit представлен как набор предположений (assumptions) и действий (actions). После конфликта writer проверяет, остаются ли assumptions истинными в текущем состоянии таблицы. Если да, actions можно безопасно применить повторно и выполнить commit.

Например, compaction может заменить `file_a.avro` и `file_b.avro` на `merged.parquet`. Такой commit безопасен, пока таблица всё ещё содержит оба исходных файла. Если один из них был удалён конфликтующим commit, операция должна завершиться ошибкой. Иначе можно безопасно удалить исходные файлы и добавить объединённый файл.

## Совместимость

Поскольку Iceberg не полагается на listing и rename файлов как на основу commit protocol, Iceberg-таблицы совместимы с любым object store. Consistent listing не требуется.
