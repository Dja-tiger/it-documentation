# От имени таблицы к файлам

SQL-движок выполняет запрос. Iceberg описывает, какие файлы составляют таблицу и как безопасно изменять это состояние. Parquet, ORC или Avro хранят сами строки. Каталог позволяет по имени таблицы найти её актуальные метаданные и обеспечивает механизм публикации изменений, зависящий от реализации каталога.

Пример `lab.training.events`: `lab` — каталог Spark, `training` — namespace, `events` — таблица. Это логическое имя; оно не обязано совпадать с путём к файлам.

## Что читает движок

| Уровень | Что содержит | Зачем нужен |
| --- | --- | --- |
| Каталог | Способ найти актуальные метаданные таблицы | Разрешить имя и опубликовать commit |
| Table metadata JSON | Схемы, partition specs, snapshots и текущий snapshot | Описать состояние таблицы |
| Snapshot / manifest list | Список manifests и сводную статистику партиций | Выбрать нужные manifests |
| Manifest | Пути к data/delete files, состояние записей и статистику | Выбрать файлы для чтения |
| Data files | Строки в Parquet, ORC или Avro | Получить данные |
| Delete files, когда используются | Информацию об удалениях | Исключить удалённые строки при чтении |

Читатель не собирает таблицу из всех файлов, найденных в директории. Файл может существовать в хранилище и не входить в выбранный snapshot. Поэтому ручное копирование Parquet в директорию не является INSERT, а ручное удаление файла может повредить доступные версии таблицы.

В лабораторной посмотрите `events.snapshots`, `events.files`, `events.manifests`. Сопоставьте `record_count` и `file_size_in_bytes` с обычным `SELECT`. Статистика файлов помогает планированию, но сумма `record_count` по data files не является универсальным способом получить число видимых строк при наличии delete files.

## Схема: имя и идентификатор

Iceberg отслеживает поля по уникальным ID. При переименовании поля ID сохраняется, поэтому старые файлы можно читать под новым именем. Добавленное заново поле с прежним именем получает другой ID и не должно случайно прочитать удалённые значения.

Добавление, удаление, переименование и допустимое расширение типа меняют метаданные. Они не означают, что произвольное преобразование типа безопасно: допустимые изменения перечислены в [эволюции схемы](../docs/evolution.md).

Практика: добавьте `source STRING`, затем переименуйте его в `origin`. Старые строки должны иметь `NULL` в новом поле; после отдельного INSERT новая строка получит заданное значение.

## Скрытое партиционирование

При `PARTITIONED BY (days(event_time))` writer вычисляет значение партиции из `event_time`, а читатель может фильтровать сам `event_time`. Пользователю не требуется вручную поддерживать ещё одну колонку `event_date` и согласовывать с ней каждый запрос.

Изменение `days(event_time)` на `months(event_time)` создаёт новую спецификацию. Старые файлы сохраняют прежнюю. Планировщик учитывает спецификацию каждого файла; автоматической перезаписи старых файлов не происходит.

В лабораторной после изменения partition spec посмотрите `spec_id` в `events.files`. После записи новых строк должны одновременно существовать файлы с разными `spec_id`.

## Проверка понимания

**Задание:** в таблице переименовали поле, поменяли days на months и выполнили один INSERT. Какие файлы обязательно переписаны?

**Ответ:** операции изменения схемы и partition spec сами по себе не переписывают существующие data files. INSERT создаёт новые файлы; новые записи используют актуальную схему и спецификацию. Новые metadata files фиксируют изменения. Конкретное число файлов зависит от движка и его настроек записи.
