# Правила самостоятельного изучения Go

## Mastery, а не «прочитал страницу»

Тема считается изученной, когда я могу без подсказки:

1. объяснить концепцию своими словами;
2. написать минимальный рабочий пример;
3. предсказать поведение небольшого фрагмента кода до запуска;
4. намеренно получить типичную ошибку или неверное поведение;
5. объяснить, почему это произошло;
6. исправить проблему корректным Go-паттерном;
7. применить концепцию в задаче, близкой к реальному pipeline/backend-коду.

Если выполняются только пункты 1–2, тема ещё не закреплена.

## Основной цикл изучения

Для каждой темы работаем в одном порядке:

```text
прочитать официальный материал
        ↓
воспроизвести минимальный пример
        ↓
написать свой пример без копирования
        ↓
изменить/сломать его
        ↓
предсказать результат
        ↓
проверить compiler/runtime/tooling
        ↓
объяснить расхождение, если оно было
        ↓
применить в exercise/project
```

Документация остаётся reference. Не нужно запоминать API целиком: нужно понимать модель и уметь быстро найти точный контракт.

## Правило повторения Day 0 / 1 / 3 / 7 / 14

Календарь здесь не создаётся. После фактического первого изучения темы используйте интервалы относительно своего Day 0.

### Day 0 — изучить и написать

- прочитать материалы stage;
- запустить официальные примеры;
- написать минимальный пример самостоятельно;
- выполнить основной exercise;
- зафиксировать, что оказалось неожиданным.

### Day 1 — воспроизвести без документации

- не открывая notes, объяснить концепцию;
- заново написать минимальный пример;
- свериться с документацией только после попытки.

### Day 3 — короткая задача

Решить новый вариант задачи с той же концепцией. Не копировать код Day 0.

### Day 7 — контрольные вопросы

Ответить вслух или письменно на вопросы `Проверка себя` соответствующего stage. Затем выполнить один intentional-break experiment.

### Day 14 — интеграция

Использовать концепцию в более крупной задаче или текущем project checkpoint. Если приходится постоянно смотреть базовый syntax, тему вернуть в активное повторение.

## Как читать документацию

Не читать весь `docs/` линейно.

Для каждого stage:

1. пройти документы из `## Прочитать` по порядку;
2. открыть Specification только по указанным точечным вопросам;
3. открыть pkg.go.dev для точного API package;
4. после практики вернуться к `Effective Go`/Specification — они становятся значительно полезнее после собственного кода.

## Как работать с A Tour of Go

Tour — официальный внешний интерактивный ресурс, а не часть локального перевода. Используйте его для syntax/core language и concurrency. Если в `docs/tutorial/` уже есть локальная последовательность по теме, сначала проходите её.

## Правило «сначала предсказать»

Перед запуском изменённого примера записать ожидаемый результат. Особенно для:

- `len`/`cap` и `append`;
- map lookup;
- pointer/nil;
- typed nil в interface;
- channel buffering/close;
- races/deadlocks;
- context cancellation;
- database pool limits.

Цель — построить корректную mental model, а не просто наблюдать output.

## Правило intentional failure

Ошибку создаём в безопасной локальной среде, затем отвечаем на четыре вопроса:

1. Что именно сломалось: compile time, panic, deadlock, race, timeout, resource exhaustion или logical bug?
2. Какой diagnostic дал compiler/runtime/tool?
3. Какой контракт Go был нарушен?
4. Какой минимальный исправляющий design?

Для race используйте `go test -race`/`go run -race`. Для deadlock и pool exhaustion ставьте timeout, чтобы эксперимент гарантированно завершался.

## Что считать хорошей практикой

Упражнение считается выполненным, если:

- код проходит `gofmt`;
- `go test ./...` успешен;
- там, где есть concurrency, `go test -race ./...` успешен;
- ошибки не игнорируются без обоснования;
- cleanup/cancel functions вызываются;
- нет неограниченного роста goroutines/queues;
- README кратко фиксирует contract и команды запуска.

## Когда переходить к следующему stage

Не ждать ощущения «я знаю всё». Переходить, когда выполнен `Критерий завершения` stage и базовую задачу можно написать с нуля. Детали API остаются в reference — это нормально.
