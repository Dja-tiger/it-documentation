# От наблюдения к обслуживанию

Начинайте с измерения. Размер таблицы в строках не объясняет ни длительность планирования, ни число открываемых файлов, ни объём прочитанных байтов.

```sql
SELECT count(*) AS files,
       sum(file_size_in_bytes) AS bytes,
       min(file_size_in_bytes) AS smallest,
       max(file_size_in_bytes) AS largest
FROM lab.training.events.files
WHERE content = 0;

SELECT * FROM lab.training.events.partitions;
```

Сравните эти данные с планом запроса (`EXPLAIN`) и метриками его исполнения. Фильтр на partition transform и статистика колонок позволяют отсечь файлы при планировании. В лабораторной проверяется содержимое таблицы и изменение числа файлов; она не является нагрузочным тестом.

## Четыре независимые операции

| Операция | Что решает | Чего ожидать |
| --- | --- | --- |
| `rewrite_data_files` | Много мелких файлов, необходимость иной организации данных | Новые data files и snapshot; строки должны сохраниться |
| `rewrite_manifests` | Неудачная организация manifests | Изменение metadata index; это не compaction самих данных |
| `expire_snapshots` | Избыточная история | Утрата time travel к удалённым snapshots; очистка файлов, не нужных сохраняемым версиям |
| `remove_orphan_files` | Файлы без ссылок из метаданных, например после неудачных записей | Поиск по хранилищу и сверка с метаданными; это отдельная задача |

В лабораторной два INSERT в непартиционированную таблицу создают мелкие файлы. `rewrite_data_files` вызывается с `rewrite-all=true`, чтобы маленький учебный набор гарантированно попал в обработку. Для рабочего обслуживания это не готовая универсальная настройка: переписывание всех файлов может быть дорогим.

## Retention и активные writers

Retention определяют по требованиям восстановления, длительности запросов и загрузок, задержкам downstream consumers, branches и tags. Значение из демонстрации не следует переносить в рабочий кластер без этого расчёта.

Для orphan cleanup сначала используйте `dry_run => true`. Даже просмотр кандидатов выполняет обращение к файловой системе. Не сокращайте период хранения ниже максимально ожидаемого времени записи: файлы ещё работающего writer могут оказаться не опубликованы в метаданных. Также сравнивайте схемы и authority путей, чтобы один физический файл не выглядел как два разных URI.

```sql
CALL lab.system.remove_orphan_files(
    table => 'training.compaction_demo',
    dry_run => true
);
```

Автоматическая лабораторная выполняет только этот просмотр; physical orphan deletion и expiration в неё не включены. Для них сначала нужна отдельная копия данных и выбранная политика retention.

## Почему ускорение не гарантировано

Объединение файлов уменьшает overhead их открытия, но не исправляет любой медленный JOIN, нехватку ресурсов или неудачную фильтрацию. Слишком крупные файлы могут ограничить параллелизм. Сортировка может улучшить pruning по одним колонкам и не помочь другим.

**Задание:** число data files снизилось с 1000 до 20, но запрос не ускорился. Что смотреть?

**Ответ:** план и метрики: какие файлы и байты реально прочитаны, сколько задач выполняется, есть ли shuffle/skew, где проходит основное время. Затем сравнить запрос до/после на одинаковых данных и ресурсах.
