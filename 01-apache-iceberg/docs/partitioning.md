# Партиционирование

## Что такое партиционирование?

Партиционирование — способ ускорять запросы за счёт группировки похожих строк во время записи.

Например, запросы к таблице логов `logs` обычно содержат временной диапазон. Следующий запрос ищет записи между 10:00 и 12:00:

```sql
SELECT level, message FROM logs
WHERE event_time BETWEEN '2018-12-01 10:00:00' AND '2018-12-01 12:00:00';
```

Если настроить таблицу `logs` на партиционирование по дате `event_time`, события одного дня будут сгруппированы в файлах с одинаковой датой. Iceberg хранит эту дату в метаданных и использует её, чтобы пропускать файлы других дат, где заведомо нет нужных данных.

Iceberg умеет партиционировать timestamp по году, месяцу, дню и часу. Также можно использовать категориальную колонку, например `level`, чтобы физически располагать похожие строки вместе и ускорять запросы.

## Чем подход Iceberg отличается?

Другие табличные форматы, например Hive, также поддерживают партиционирование, но Iceberg реализует **hidden partitioning — скрытое партиционирование**.

- Iceberg берёт на себя рутинное и подверженное ошибкам вычисление partition values для каждой строки.
- Iceberg автоматически исключает ненужные партиции. Потребителям данных не требуется знать, как физически партиционирована таблица, и добавлять дополнительные фильтры.
- Partition layout можно эволюционно изменять.

### Партиционирование в Hive

Чтобы увидеть разницу, рассмотрим таблицу `logs` в Hive.

В Hive партиции явные и представлены как колонка, поэтому таблица `logs` имела бы колонку `event_date`. При записи `insert` обязан передать значение `event_date`:

```sql
INSERT INTO logs PARTITION (event_date)
  SELECT level, message, event_time, format_time(event_time, 'YYYY-MM-dd')
  FROM unstructured_log_source;
```

Аналогично, запрос по `logs` должен содержать фильтр по `event_date` дополнительно к фильтру по `event_time`:

```sql
SELECT level, count(1) as count FROM logs
WHERE event_time BETWEEN '2018-12-01 10:00:00' AND '2018-12-01 12:00:00'
  AND event_date = '2018-12-01';
```

Если фильтр `event_date` отсутствует, Hive просканирует все файлы таблицы, потому что не знает о связи `event_time` и `event_date`.

### Проблемы партиционирования Hive

Hive необходимо явно передавать partition values. В примере с логами Hive не знает связи между `event_time` и `event_date`.

Это приводит к нескольким проблемам:

- Hive не может валидировать partition values — ответственность лежит на writer:
  - неправильный формат, например `2018-12-01` вместо `20181201`, приводит к тихо неверным результатам, а не к ошибке запроса;
  - неправильная исходная колонка, например `processing_time`, или неверный часовой пояс также дают неправильные результаты без явной ошибки;
- корректность запросов зависит от пользователя:
  - неправильный формат также даёт незаметно неверный результат;
  - пользователи, не знающие физического layout таблицы, получают неоправданно медленные запросы, поскольку Hive не умеет автоматически преобразовывать фильтры;
- работающие запросы связаны с конкретной схемой партиционирования, поэтому изменить её без поломки запросов нельзя.

### Скрытое партиционирование Iceberg

Iceberg самостоятельно получает partition value из значения исходной колонки, при необходимости применяя transform. Iceberg сам преобразует `event_time` в `event_date` и хранит информацию об этой связи.

Partition spec задаётся через такие отношения. Для таблицы `logs` это могло бы быть `day(event_time)` и `level`.

Поскольку Iceberg не требует пользовательских partition columns, физическое партиционирование можно скрыть. Partition values всегда вычисляются единообразно и, где возможно, автоматически используются для ускорения запросов. Producers и consumers вообще не обязаны видеть `event_date`.

Главное следствие: запросы больше не зависят от физического layout таблицы. Отделение логической модели от физической позволяет Iceberg менять схему партиционирования со временем по мере роста объёма данных. Ошибочно спроектированную схему можно исправить без дорогостоящей миграции всей таблицы.

Полный список поддерживаемых transforms см. в официальной спецификации Iceberg, раздел `Partition Transforms`.

Обновление partition spec описано в [[evolution#Эволюция партиционирования|эволюции партиционирования]].
